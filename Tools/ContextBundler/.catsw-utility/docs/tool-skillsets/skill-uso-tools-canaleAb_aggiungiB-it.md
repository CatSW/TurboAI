# Agentic Governance TDM 1.0: Channel A + Channel B

## Overview

This skill defines the operational rules and role division for executing development tasks.

---

## 1. Channel Architecture and Roles

### Channel A — Operational Agent (Executor)

* **Role:** Modifies C# source code and project files (`.csproj`) if necessary to add dependencies. Compiles and runs unit tests.
* **Reading Scope:** Consults `.ai-context/canale-a/<project>/AGENT_CONTEXT.md` and relevant code if needed.
* **Prohibitions:** 
  * NEVER directly modifies files in `Documentation/`, `Changelog.md`, or Plan files in `.ai-context/`.
  * NEVER generates intermediate state files.
* **Mandatory Chat Output:**
  1. **Operational Report:** Execution status (`PASS`/`FAIL`), executed tests, modified code/project files.
  2. **Changelog Delta:** A single, isolated, and copy-pasteable Markdown block containing the modifications formatted strictly according to **Keep a Changelog 1.1.0**.

### Channel B — Control Tower (Supervisor)

* **Role:** Performs code review on the modifications made by Channel A (left in a *dirty* state on the repository).
* **Document Management:** Takes the delta produced by Channel A and pastes it into `Changelog.md` inside `<project>/Documentation/`.
* **State Progression:** Updates the Plan in `.ai-context/` and provides the task-closing commit script (including the upcoming call to the Python tool to move the `<next_task>` marker).

---

## 2. Changelog Delta Standard (Keep a Changelog)

Channel A must format the isolated Changelog block following the [Keep a Changelog](https://keepachangelog.com/it-IT/1.1.0/) specifications.

---

## 3. Agentic Artifact Isolation

* **Product Transparency:** All product documentation inside `Documentation/` and `README.md` files must remain entirely agnostic, clean, and free of references to the use of AI, prompts, or agentic logs.
* **Segregation:** The entire agentic governance dashboard resides exclusively in the hidden `.ai-context/` folder and the unreleased `.github/` folder.

# skill-turbo-ai-tools-use-channel-b-en

## Skill - Using CatSW tools in LLM chat

Audience: LLM. Purpose: acquire context, request Python/PowerShell commands, generate artifacts, verify patches via `.catsw-utility`.
Session: a single PowerShell session in `<repo-root>\.catsw-utility`. No new windows/consoles/directory changes if the current session suffices.

### 0. Authority and document interpretation

- Distinguish LLM-facing instructions from user-facing manuals; do NOT reinterpret a manual as an operational procedure.
- A file under `.catsw-utility/docs` is NOT automatically a skill: the declared title, purpose, and audience govern.
- If the bundle includes this file, read it BEFORE proposing commands/context-request/requests.
- User request conflicts with a previous LLM proposal → stop the wrong proposal, apply the correction immediately.
- Do NOT generate a ContextBundler context-request just because it's available: first check whether discovery has already been done and what's actually missing.
- User writes `go` → proceed directly with the step already proposed, no further confirmation needed.

### 1. General principles

- Incremental, verifiable; targeted discovery before making changes.
- ContextBundler > requesting individual files when it's more efficient.
- Do NOT simulate build/test/pack/verification. Do NOT treat empty output as an automatic error.
- Do NOT propose a commit until scope, whitespace, and untracked files have been checked.
- Always: absolute path of requested files + full destination path of produced artifacts.
- Paths relative to `.catsw-utility` for CatSW tools, `..` for repo root. `Push-Location`/`Pop-Location` only when another directory is genuinely needed — never ask for a second console.
- The user's local automation (background watcher + unified orchestrator `process-from-llm`) picks up every `FromLlm-*` and `context-request-*.md` download on its own, sanitizes any "adorned" filenames produced by the chat channel, and applies/processes it. NEVER name a `.cmd`/script for the user to run, and NEVER ask the user to move, extract, or unblock a file manually — deliver the download and nothing else operational (§5.2, §7, §11).
- Scripts generated by the LLM = `.py` by default; `.ps1` only for backward compatibility/explicit request (§5).
- Output in `ToLlm.txt` → suggest Notepad++ **Tail mode** before running.

### 2. Starting a session

**2.1 Without a startup bundle** (no `context-out-start-session-*.md` attached):
1. user opens/keeps 1 PowerShell in `.catsw-utility` (verify with `Get-Location` if needed);
2. run `ListFiles.cmd`;
3. ask for `ls.txt`;
4. analyze Git baseline, working tree, inventory;
5. targeted `rg` if needed (paths relative to root via `..`);
6. ContextBundler context-request ONLY after discovery.

**2.2 With a startup bundle** (`context-out-start-session-*.md` from `startup-llm-session.cmd`):
- read it in full BEFORE asking for anything else;
- `File: .catsw-utility/ls.txt` section present → `ListFiles.cmd` already run, do NOT request it again nor request `ls.txt` separately;
- from `ls.txt`: inventory, last commit, Git baseline, working tree;
- read the skill/governance/context docs already included in the same bundle;
- do NOT immediately generate a new context-request: first determine what's actually missing; request only the targeted discovery/rg/files/supplementary bundles actually needed.

Repeat `ListFiles.cmd` ONLY IF: the `ls.txt` section is missing/incomplete/errored, OR the user reports the repo has changed, OR an intentional refresh of the repo snapshot is needed.

**2.3 Evaluating governance/context documents**

3 possible situations (don't presume which one upfront): (1) rough first setup — empty fields/typos/plausible inconsistencies; (2) already-complete first setup; (3) resumption of a previous session with a reliable handoff.

Procedure:
- compare baseline/working tree/build-test status/next tasks/names/paths across the documents;
- distinguish an intentionally-empty field from an accidental omission;
- relevant problem/contradiction/typo/ambiguity/insufficient info → **flag it BEFORE proceeding**, stating the file, the point, the practical impact, and the decision needed;
- cosmetic difference with no ambiguity → don't block (but log it if within the update task's scope);
- no substantial problem → proceed directly, no superfluous confirmations;
- do NOT automatically assume either defect or completeness; do NOT overwrite established conclusions or repeat already-completed tasks just because the chat session is new.

Decision rule: **substantial problem → flag first** | **clear and sufficient → proceed** | **missing but recoverable → minimal targeted discovery, without restarting the whole flow**.

**2.4 Repository portability**

Instructions/ZIPs/scripts must work without manual changes in repos at different paths. Never hardcode a solution path, username, or a specific solution filename.

Base for scripts under `.catsw-utility` (PowerShell):
```powershell
$UtilityRoot = $PSScriptRoot
$RepositoryRoot = Split-Path -Parent $UtilityRoot
$DownloadsRoot = Join-Path ([Environment]::GetFolderPath('UserProfile')) 'Downloads'
$OutputFile = Join-Path $DownloadsRoot 'ToLlm.txt'
```
Rules: always derive repo root from the parent of `$PSScriptRoot`; use `git -C $RepositoryRoot ...`; paths relative to root for projects/files/rg; discover `*.slnx` first, then `*.sln`; no solution found → explicit error; multiple solutions + non-unique task → accept a relative parameter or stop (never pick arbitrarily); build `ToLlm.txt` in the current user's `Downloads` without hardcoding home/username; create `Downloads` only if possible, otherwise stop with a clear message; NEVER hardcode absolute paths specific to a solution (ReportGenerator, ApigeeAuth, PartnerApi, etc.).

### 3. Single rg command

`rg <options> <pattern> .. | Set-Clipboard` in the session already open in `.catsw-utility`. Then ask the user to paste the clipboard content into chat.
Use `$OutputFile` instead of the clipboard ONLY if output is large or multiple commands need to be collected.

### 4. Multi-command PowerShell blocks

A single copy-paste block for the session already in `.catsw-utility`.

Rules:
- `cls` as the first command; NO initial `Set-Location` if already in the canonical dir (if essential to guarantee it: `Get-Location` or a single `Set-Location '<repo-root>\.catsw-utility'` at the start);
- output into `$OutputFile`: `>` on the first write, `>>` on subsequent ones; a readable header before each command (e.g. `PS> git -C .. status --short`); `2>&1` where appropriate; sections separated by `"" >> $OutputFile`;
- **last command of the block = always `Write-Host "Premi Invio o ESC 😄"`** (also for short sequences like `Unblock-File` + script execution: without this, the last pasted line stays suspended waiting for Enter); leave a blank line after it if the renderer preserves it; this message replaces any separate notice about pressing Enter/Esc;
- do NOT use a trailing backtick, a PS comment, or a whitespace-only line as the final sentinel;
- ask the user to attach `$OutputFile` via drag&drop;
- Git run from `.catsw-utility` → `git -C .. <command>`; `dotnet` → relative path (e.g. `dotnet build ..\GpgCripto.slnx`);
- do NOT compact scriptblocks/redirections: keep spaces around `>`, `>>`, `2>&1` (never `$Command>>$OutputFile`);
- fail-fast: no `--no-build` test after a failed restore/build;
- Notepad++ **Tail mode** for `$OutputFile`.

Standard template:
```powershell
cls
$DownloadsRoot = Join-Path ([Environment]::GetFolderPath('UserProfile')) 'Downloads'
$OutputFile = Join-Path $DownloadsRoot 'ToLlm.txt'
"PS> git -C .. status --short" > $OutputFile
git -C .. status --short >> $OutputFile 2>&1
"" >> $OutputFile
"PS> dotnet build ..\<solution-file>" >> $OutputFile
dotnet build ..\<solution-file> >> $OutputFile 2>&1
"" >> $OutputFile
Write-Host "Premi Invio o ESC 😄"

```

**4.1 PowerShell token mutilation (`::`) (console/legacy `.ps1` only — not applicable to Python)**

The chat renderer can mutilate `::`: the full expression `[Environment]::GetFolderPath('UserProfile')` risks appearing/being copied as `(:GetFolderPath('UserProfile'))`.

Rules:
- command containing `::` → NEVER a plain copyable block: always generate a downloadable `.ps1`;
- before delivery: programmatically verify the literal presence of the full expected token (e.g. `[Environment]::GetFolderPath`) AND the absence of known mutilated variants (e.g. `(:GetFolderPath`);
- absolute destination path; run from the canonical session; CRLF unless a different verified repo convention applies; apply `Unblock-File`;
- don't automatically attribute the error to the user: distinguish generated source / downloadable file / chat rendering.

Minimum secondary check: full token (positive), mutilated variants (negative), CRLF, expected name, non-zero size.
This rule OVERRIDES the general preference for pasteable blocks: with `::`, delivery as `.ps1` is mandatory.

### 5. Complex scripts generated by the LLM

Standard: Python, `FromLlm-<script-name>.py`. `.ps1` only for backward compatibility (§5.1).

Rules for `.py`:
- repo root: `Path(__file__).resolve().parent.parent` (script lives under `.catsw-utility`);
- output: `Path.home() / "Downloads" / "ToLlm.txt"`, never hardcode username/home;
- external commands (git, dotnet...): `subprocess.run(..., check=False)`, capture stdout/stderr/exit code, no unhandled exceptions on a failed command;
- fail-fast: don't proceed with subsequent checks (e.g. tests after a failed build) if a prior step failed;
- FORBIDDEN: destructive Git operations (`reset --hard`, `clean`, `checkout` on tracked files, `push`), automatic commits — except with explicit exemption for closing a verified milestone;
- `ToLlm.txt`: UTF-8, LF;
- provide only the download link; NEVER mention running, moving, or unblocking anything — the user's local automation handles it (§1, §5.2);
- standard library only (`pathlib`, `subprocess`, `shutil`, `zipfile`, `json`, `re`), no external dependencies not already present;
- never a second console.

**5.1 Backward compatibility with `.ps1`**: valid only for pre-existing scripts or an explicit user request; do NOT generate new `.ps1` scripts by default. Historical rules still apply: root from `$PSScriptRoot`, `git -C $RepositoryRoot`, CRLF, `Write-Host "Premi Invio o ESC 😄"` as the last command (§4), `Unblock-File`.

**5.2 Automatic application of ZIPs/single scripts (unified orchestrator)**

The user's local automation applies every `FromLlm-*` and `context-request-*.md` download entirely on its own:

- A background watcher (`from-llm-watcher`) detects a stable file in Downloads.
- It launches the single unified entry-point `process-from-llm.cmd` → `process-from-llm.py`.
- The orchestrator:
  1. Selects the most recent matching file (context-request or FromLlm artifact).
  2. Sanitizes any "adorned" filename produced by the chat channel (e.g. `Scarica 'FromLlm-Patch.zip'.zip` → `FromLlm-Patch.zip`) and logs a WARNING.
  3. Routes:
     - `context-request-*.md` → leaves the file in Downloads and launches ContextBundler.exe (SmartAssFileResolver already searches Downloads).
     - `FromLlm-*.{py|ps1|zip}` → delegates to the existing zip/script processing logic.
  4. Archives the original file from Downloads into `.catsw-utility/history/` with a timestamp prefix (prevents re-processing and name collisions).

Extraction, moving, execution, timestamp touch (T4.1), and cleanup all happen without any action from the user beyond downloading the file. The LLM has no visibility into and no control over this mechanism, and must never describe it, name any `.cmd`/script involved, or ask the user to run/move/unblock/extract anything. The only responsibility of the LLM is to deliver a correctly-named download (§10.1) and, if a result is needed for the next step, ask the user to attach the relevant output (e.g. `ToLlm.txt`, §12) once it's available.

Common constraints on what the LLM delivers, regardless of how it gets applied: no container directory in a ZIP; the script verifies the patch or performs the requested operation, derives its root from the parent of its own location, is portable; staging/commits/destructive Git/automatic deployment are FORBIDDEN; only external write = `ToLlm.txt` in Downloads; fail-fast verification.

### 6. Interpreting Git output

- `git status --short` empty → working tree normally clean.
- `git diff --check` empty → normally no issues found on the examined tracked files.
- `git diff`/`--stat`/`--check` normally do NOT include untracked files → if new files are present: explicit staging + check the cached diff too.
- After an `amend`: consider the previous hash superseded, use only the new one as baseline.
- From `.catsw-utility`: run Git as `git -C .. ...`.

**Baseline-Hash-Ref.md** (never tracked): the hash is born AFTER the commit.
1. The LLM, in a milestone/iteration closing script, may append a single placeholder line: `- <textual milestone/iteration description>: <hash_to_be_updated_by_user_after_commit>`.
2. After the commit, the user replaces only the placeholder with the real hash from `git log -1 --oneline`.
3. The LLM must NEVER regenerate the whole Baseline-Hash-Ref.md file.
4. Tracked documents (Plan/Governance/Log) show only the textual description, never the hash.

### 7. ContextBundler context-request

A downloadable Markdown file with a descriptive name (e.g. `context-request-t6.3-orchestration.md`).
Must: start with `# Files to bundle`; use paths relative to the repo root; include only the files/line ranges genuinely needed; follow the syntax/limits of the current ContextBundler version; use LF line endings.
Provide only the download link. Never mention a destination path or ask the user to move/run anything — the user's local automation picks it up and processes it on its own (§1, §5.2). When the resulting bundle is needed, ask for `<repo-root>\.catsw-utility\context-out-<description>.md`.

### 8. Processing context-out.md

Check: the reported Git baseline + working tree; the count/inclusion of requested entries; any omitted ranges or limits flagged by the tool; escaping/Markdown fences introduced by the bundler (do NOT carry these into source files).
Do NOT blindly reconstruct files if the bundle's context is insufficient; only expand the bundle with a new iteration when actually necessary.

### 9. Attachments received via Copilot for Microsoft 365

The user's Copilot for Microsoft 365 interface does not support attaching `.zip` files.

- do NOT ask the user to re-attach a ZIP file if the interface doesn't support it;
- it IS allowed and preferable for the LLM to deliver a multi-file patch to the user as a downloadable ZIP to extract at the repo root;
- when multiple files are needed, respect the formats actually supported by the chat, and where possible use ContextBundler to produce a single Markdown file;
- the user's local source file is the authoritative reference;
- the conversion/rendering layer between Copilot for Microsoft 365 and the LLM's tooling can alter how attached content is displayed, e.g. introducing escaping, backslashes, fences, serialization, or other normalizations not present in the source;
- these transformations happen outside the user's control and must NOT be automatically attributed to the local file, to ContextBundler, or to a user error;
- do NOT diagnose corruption, incorrect escaping, or accidental fences in the source based solely on the representation received from the tool;
- always distinguish between: source file content / legitimate delimiters added by ContextBundler / intentionally empty fields / transformations introduced by the attachment channel;
- an empty field expected by the task must be treated as information to be completed, not as a conversion artifact;
- before "correcting" a suspected formatting anomaly, look for confirmation in the real file, a screenshot provided by the user, a targeted output, or a hash;
- if the source can't be verified, describe the anomaly as a possible representation transformation, not as a confirmed defect in the file.

### 9.1 Mandatory naming for downloadable artifacts

Every ZIP and every LLM-generated script (`.py` by default, `.ps1` only for backward compat/explicit request, §5) delivered to the user for download MUST carry the EXACT prefix `FromLlm-` (case-sensitive).

- ZIP: `FromLlm-<descriptive-name>.zip`;
- script: `FromLlm-<descriptive-name>.py` (default) or `.ps1` (backward compat);
- also applies to scripts included inside a ZIP;
- application/documentation files contained in the patch keep their original name and do NOT receive the prefix, unless the user explicitly requests it;
- before delivery, programmatically verify the final file name + the `.py`/`.ps1` entries in the ZIP;
- FORBIDDEN variants: `FromLLM-`, `FromLMM-`, `fromLlm-`, `FromLlm_`, or a missing prefix.

Valid examples: `FromLlm-ReportGenerator-documentation-2b-2c.zip`; `FromLlm-verify-nullable-warning-fix.py`; `.catsw-utility/FromLlm-verify-patch.py` (ZIP entry); `FromLlm-verify-legacy-fix.ps1` (backward compat only).

**9.2 Link label = physical file name**

The clickable label and the physical artifact name must match EXACTLY.

- link text = ONLY the full physical file name (e.g. `[FromLlm-elabora.ps1](...)`, `[context-request-t4.2-smoke-test-operativo.md](...)`);
- FORBIDDEN: prefixes like "Download"/"File" or other descriptions inside the label; backticks/quotes/extra parentheses inside the label;
- any "Verified physical name" / "Initial destination" / instructions text: kept SEPARATE from the link;
- before delivery, verify separately: requested name, saved physical name, the tool's returned `fileName`, and the exact label text;
- if the user reports a different name after downloading, explicitly distinguish between the generated artifact, the tool's metadata, and a name imposed by the download channel; do NOT automatically attribute the discrepancy to the user;
- `context-request-*.md` files: do NOT apply the `FromLlm-` prefix, keep the canonical `context-request-<description>.md` name as the link label.

Correct: `[FromLlm-elabora.ps1](ref)`. Wrong: `[Download FromLlm-elabora.ps1](ref)`, `` [Download `FromLlm-elabora.ps1`](ref) ``, `` [`FromLlm-elabora.ps1`](ref) ``.

### 10. Generating and delivering artifacts

- Always provide downloadable files, never text for manual reconstruction.
- The `FromLlm-` prefix is mandatory on ZIPs and scripts (including inside a ZIP).
- Multi-file patch → a single ZIP to extract at repo root; structure relative to root + original file names preserved exactly; NO extra container directory (the first entry must be a direct patch path, e.g. `Project/File.cs`, `.catsw-utility/FromLlm-verify-patch.py`).
- Always state the absolute extraction root path + full destination paths of the main files (informational only — the user's local automation applies the file on its own, §5.2).
- Include at most one script: `.catsw-utility/FromLlm-*.py` (or `.ps1` backward compat). Portable: for Python → derive root from `Path(__file__).resolve().parent`; for legacy `.ps1` → `$PSScriptRoot`. Never hardcode repo-specific absolute paths.
- The script produces `ToLlm.txt` (Notepad++ Tail mode); it verifies the extracted patch.
- Never name a `.cmd`/script for the user to run, or ask them to extract/move/unblock the file — deliver the download only (§1, §5.2).
- A single script without a ZIP is allowed: provide only the link `FromLlm-<script-name>.py` (or `.ps1` backward compat) — no run instructions, no manual commands (§5.2).
- Line endings: CRLF for `.cs`; LF for `.md`/`.json`/`.yml`/`.yaml`/`.py`; CRLF for legacy `.ps1` (unless a different verified repo convention applies).
- A PowerShell command (console or legacy `.ps1`) containing `::` → never a copyable block, programmatic token verification required (§4.1); not applicable to Python.
- Secondary pre-delivery ZIP check: entries/relative paths, no path traversal/unexpected container directory, names, file count, non-zero sizes, line endings, no accidental Markdown fences.
- Before publishing the response: link label = physical name only, matching the tool's `fileName` character-for-character (no "Download"/backticks/descriptions).
- Secondary check: ZIP name starts with `FromLlm-`; every `.py`/`.ps1` entry starts with `FromLlm-`.
- NEVER include credentials/tokens/sensitive output/build artifacts/out-of-scope files.

### 11. Verification after a patch

Everything from the single PowerShell session in `.catsw-utility`, without permanently changing directory. `ToLlm.txt` → Notepad++ Tail mode.

Request at least: relevant build/tests (relative paths, e.g. `..\GpgCripto.slnx`); `git -C .. status --short`; `git -C .. diff --stat`; `git -C .. diff --check`.

If untracked files are present → explicit staging of only the expected files, then: `git -C .. diff --cached --check`; `git -C .. diff --cached --stat`; `git -C .. status --short`.

**Before proposing a commit the LLM MUST:**

1. **Provide the Changelog delta** in Keep a Changelog format (https://keepachangelog.com/it-IT/1.1.0/).  
   Deliver only the new entries to be inserted under the current version section.  
   Do **not** read or rewrite the entire Changelog.md — this saves tokens and leaves the authoritative file under user control.  
   The user inserts the delta manually.

2. **Remind the user to move the `<next_task>...</next_task>` tags** in the plan file to the next task (or to a completion marker if the plan is finished) **before** the commit.

Only after the user has confirmed the Changelog update and the tag move may the LLM propose the final commit message and the verification commands (`git log -1`, `status --short`).

Propose a commit ONLY after positive results. After the commit, request: `git -C .. log -1 --oneline`; `git -C .. status --short`.

### 12. Operational summary rule

`.catsw-utility` structure:
- root: `.cmd` wrappers (now primarily the unified `process-from-llm.cmd`) + current files — the LLM does not need to know or reference them individually (§1, §5.2);
- `artifacts`: `.exe`, current `.py` (including `process-from-llm.py` and `from-llm-watcher.py`), legacy `.ps1` — never run directly by the user;
- `docs`: manuals (NOT automatically skills);
- `history`: archive of exhausted `FromLlm-*`/`context-request-*`/`context-out-*` files and of executed `FromLlm-*` scripts (timestamp-prefixed by the orchestrator).

The LLM never names a `.cmd`/script to the user (§1, §5.2, §10) — the only exceptions are `ListFiles.cmd` and `startup-llm-session.cmd`, which the user runs to bootstrap a session (§2.1), not something the LLM's downloads trigger. Still valid for discovery/verification: `rg ... ..`, `dotnet ... ..\<solution-file>`, `git -C .. ...`.
